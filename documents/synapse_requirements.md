## 2. 引言

### 2.1 项目定位

Synapse 是 EROS 机器人操作系统生态中的**进程间通信（IPC）中间件**。它位于操作系统基础库 Cytoskeleton 与算法库 Kinesin 之间，为机器人应用提供统一、可靠、可扩展的组件间通信能力。

命名隐喻：突触（Synapse）是神经元之间传递信号的结构。EROS 生态中：

- Cytoskeleton：细胞骨架，提供结构与基础运行时；
- Kinesin：驱动蛋白，提供高性能算法；
- Synapse：突触，提供组件间信号传递。

### 2.2 目标读者

- Synapse 核心开发者
- 基于 Synapse 构建模块的应用开发者
- 架构评审与测试人员

### 2.3 范围

本文档定义 `synapse-cpp` 第一版应满足的软件功能需求与非功能需求。范围覆盖：

- 同进程内通信
- 同设备跨进程通信
- 跨设备网络通信
- 与 Cytoskeleton 基础库的集成

## 3. 术语与定义

| 术语 | 定义 |
|---|---|
| IPC | Inter-Process Communication，进程间通信 |
| Pub/Sub | 发布订阅模型 |
| RPC | Remote Procedure Call，远程过程调用 |
| QoS | Quality of Service，服务质量策略 |
| Discovery | 服务/节点自动发现机制 |
| Transport | 传输层抽象 |
| Topic | 发布订阅中的逻辑通信主题 |
| Service | RPC 中的服务端接口 |
| Client | RPC 中的客户端接口 |

## 4. 总体设计目标

SYN-GOAL-01：Synapse 应为机器人系统提供统一的通信抽象，屏蔽底层传输介质差异。

SYN-GOAL-02：Synapse 应支持发布订阅、请求-响应、事件通知、流式通信等多种模式。

SYN-GOAL-03：Synapse 应为时间敏感型控制业务提供可配置的 QoS 与实时性保障。

SYN-GOAL-04：Synapse 应支持去中心化发现，避免单点故障。

SYN-GOAL-05：Synapse 应为 AI/ML 流水线提供高效数据流支持，包括大消息零拷贝能力。

SYN-GOAL-06：Synapse 应提供安全机制，支持认证、加密与访问控制。

## 5. 功能需求

### 5.1 通信模式（Communication Patterns）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-COMM-001 | 支持发布订阅（Pub/Sub）模型，允许一个 Publisher 对应多个 Subscriber | 高 | 单元测试验证 1:N 消息分发 |
| REQ-COMM-002 | 支持请求-响应（RPC）模型，客户端发送请求并接收响应 | 高 | 单元测试验证请求-响应匹配 |
| REQ-COMM-003 | 支持单向事件通知（Fire-and-Forget），无需响应 | 高 | 单元测试验证事件到达 |
| REQ-COMM-004 | 支持流式 RPC 或等价的持续双向数据流能力 | 中 | 单元测试验证多消息流 |
| REQ-COMM-005 | 支持共享状态/黑板模式，用于多模块共享世界模型 | 低 | 提供共享内存状态区 API |

### 5.2 传输与拓扑（Transport & Topology）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-TRANS-001 | 支持同进程内零拷贝通信 | 高 | 同进程 Publisher/Subscriber 不触发序列化拷贝 |
| REQ-TRANS-002 | 支持同设备跨进程共享内存通信 | 高 | 跨进程延迟 < 1ms（x86_64 本地测试） |
| REQ-TRANS-003 | 支持跨设备网络通信（UDP/TCP） | 高 | 支持至少 100Mbps 有效吞吐 |
| REQ-TRANS-004 | 支持机器人 ↔ MCU/实时核桥接接口设计（可委托给 HAL） | 中 | 提供抽象接口，HAL 实现具体协议 |
| REQ-TRANS-005 | 支持传输层自动选择，同设备优先共享内存，跨设备使用网络 | 中 | 根据目标地址自动选择传输 |
| REQ-TRANS-006 | 支持同一 Topic 跨多种传输透明路由 | 中 | 集成测试验证混合传输场景 |

### 5.3 发现与命名（Discovery & Naming）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-DISC-001 | 支持去中心化发现，无集中注册中心 | 高 | 多节点启动/停止后拓扑自动更新 |
| REQ-DISC-002 | 支持语义化命名，按功能路径命名 Topic/Service | 高 | 命名格式 `/component/subcomponent/name` |
| REQ-DISC-003 | 支持命名空间隔离 | 高 | 不同命名空间下同名 Topic 不冲突 |
| REQ-DISC-004 | 支持节点身份标识与健康状态 | 中 | 提供节点存活心跳与失效检测 |
| REQ-DISC-005 | 提供服务可用性查询接口 | 中 | 可查询某 Service 当前是否存在可用服务端 |
| REQ-DISC-006 | 支持跨域路由配置（不同子网/机器人） | 低 | 提供网关节点配置能力 |

### 5.4 服务质量（QoS）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-QOS-001 | 支持 Reliability 策略：Best-effort 与 Reliable | 高 | 测试不同策略下的消息到达率 |
| REQ-QOS-002 | 支持 History 策略：Keep-last 与 Keep-all，可配置深度 | 高 | 测试历史缓存行为 |
| REQ-QOS-003 | 支持 Durability 策略：Volatile 与 Transient-local | 中 | 测试订阅者晚加入时能否收到历史消息 |
| REQ-QOS-004 | 支持 Deadline 策略，监控消息发布周期 | 中 | 超 Deadline 时触发回调 |
| REQ-QOS-005 | 支持 Lifespan 策略，过期消息自动丢弃 | 中 | 测试消息 TTL 行为 |
| REQ-QOS-006 | 支持 Liveliness 策略，检测发布者存活 | 中 | 发布者异常退出时触发通知 |
| REQ-QOS-007 | 支持 Ownership 策略：Shared 与 Exclusive | 低 | 多 Publisher 场景下按策略选择 |
| REQ-QOS-008 | 支持 Priority 策略，高优先级消息优先处理 | 低 | 测试拥塞场景下的优先级调度 |

### 5.5 实时性与确定性（Real-Time & Determinism）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-RT-001 | 支持优先级感知的消息调度 | 中 | 高优先级消息低延迟处理 |
| REQ-RT-002 | 支持 Deadline 监控与超时通知 | 中 | 超 Deadline 时调用用户回调 |
| REQ-RT-003 | 提供有界延迟保证（Best-effort 级别文档化，Hard-realtime 可选） | 中 | 文档明确各传输路径延迟上限 |
| REQ-RT-004 | 支持抖动统计与告警 | 低 | 提供端到端延迟直方图 |
| REQ-RT-005 | 提供与 RTOS/实时核集成的接口扩展点 | 低 | 接口设计预留实时调度钩子 |

### 5.6 时间模型（Time Model）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-TIME-001 | 支持消息携带时间戳字段 | 高 | 每条消息包含 `timestamp` |
| REQ-TIME-002 | 支持 Wall-time、Monotonic-time 至少两种时钟域 | 中 | API 区分两种时间类型 |
| REQ-TIME-003 | 支持接收时间、发送时间、源时间戳记录 | 中 | 消息元信息包含三类时间 |
| REQ-TIME-004 | 提供跨节点时间同步能力扩展点（PTP/NTP） | 低 | 接口允许注入外部时钟源 |

### 5.7 类型系统与序列化（Type System & Serialization）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| REQ-TYPE-001 | 支持强类型消息定义 | 高 | 使用 IDL/schema 定义消息 |
| REQ-TYPE-002 | 支持 C++20 代码生成 | 高 | 从 schema 生成 C++ 结构体与序列化代码 |
| REQ-TYPE-003 | 支持跨语言类型支持扩展点（Python/Rust/Go 等） | 中 | 设计允许接入其他语言绑定 |
| REQ-TYPE-004 | 支持 Schema 演进，向后兼容字段增删 | 中 | 测试新增/删除字段后旧消费者仍可工作 |
| REQ-TYPE-005 | 支持自描述消息，便于调试与日志回放 | 中 | 提供带类型信息的消息序列化模式 |
| REQ-TYPE-006 | 支持大消息零拷贝传输（如图像、点云、Tensor） | 高 | 共享内存传输下避免用户态拷贝 |
| REQ-TYPE-007 | 支持多种序列化后端（至少支持 CDR 与一种零拷贝友好格式） | 中 | 可配置序列化器 |

### 5.8 安全（Security）

|---|---|---|---|
| REQ-SEC-001 | 支持传输层加密（TLS 或等价机制） | 中 | 跨网络通信默认启用加密选项 |
| REQ-SEC-002 | 支持节点身份认证 | 中 | 基于证书或令牌的认证 |
| REQ-SEC-003 | 支持 Topic/Service 级别访问控制 | 中 | 可配置哪些节点可读写哪些 Topic |
| REQ-SEC-004 | 支持安全审计日志扩展点 | 低 | 提供安全事件回调接口 |
| REQ-SEC-005 | 支持安全关键子系统与非安全子系统隔离 | 低 | 提供 Domain/Partition 隔离 |

以下内容不在第一版范围内，但保留扩展接口：

- 云端大规模集群编排
- 完整的 DDS 兼容性实现

- 硬实时操作系统内核集成

## 9. 验收策略

1. **单元测试**：每个功能需求对应至少一个单元测试。
2. **集成测试**：多进程、跨设备场景下的通信测试。
3. **性能基准**：定义同进程、同设备、跨设备的延迟与吞吐基准。
4. **代码审查**：关键路径需两人以上审查。
